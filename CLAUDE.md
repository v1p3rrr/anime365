# Инструкции для ассистента

## 🔴 Правило №0: секреты не коммитим

`access_token` Anime365 бессрочен, попавший в историю остаётся там навсегда.
Токены, пароли и ключи живут только в `.env.app` и `config/` — оба в `.gitignore`.
Ни в код, ни в тесты, ни в документацию, ни в примеры команд. Перед push —
`git status` и проверка диффа. Подробно: [claude/07-security.md](claude/07-security.md).

## Документация: сначала оглавление, потом кусок

Проектных документов два с лишним десятка, и вместе они тянут на полтора десятка
тысяч строк. Читать их целиком не нужно и вредно — контекст кончится раньше, чем
найдётся ответ.

**У каждого `.md` в корне, `claude/` и `docs/` сверху лежит одно и то же:**

1. блок **«Зачем этот файл / Когда открывать»** — по нему видно, тот ли это файл,
   и куда идти, если не тот;
2. таблица **«Стр. → Раздел»** со ссылками на все заголовки и **номерами строк**.

**Порядок работы такой:**

1. не знаете, где искать → [claude/00-INDEX.md](claude/00-INDEX.md), там карта
   «какой файл когда открывать»;
2. открыли файл — прочитайте **первые 60 строк**: этого хватает на сводку и
   оглавление целиком;
3. нашли нужный раздел → читайте **от его номера строки** (`Read` с `offset`,
   `limit` по расстоянию до следующего заголовка), а не файл целиком;
4. номер строки указывает на **саму строку заголовка**; берите пару строк
   запаса сверху.

Отдельно: `claude/09-decisions.md` — 186 решений `D-NN` и пять тысяч строк.
**Порядок записей в файле не совпадает с номерами**, поэтому искать `D-84`
листанием или `grep`-ом по всему файлу не надо — он есть в оглавлении.

Целиком читать файл имеет смысл ровно в двух случаях: он короче двухсот строк,
либо задача — ревизия всего документа.

## Документация: как править, не ломая оглавления

Номера строк в оглавлениях **никогда не правятся руками** — их пересчитывает
скрипт. От вас требуется одно:

```bash
python scripts/update_docs_toc.py
```

Чтобы не помнить об этом вовсе, включите хук — один раз на машину:

```bash
git config core.hooksPath scripts/hooks
```

Он пересчитает оглавления перед коммитом и донесёт в него **только те** `.md`,
которые в коммите и так были: дописывать соседнее хук не имеет права.

**Запускать после любой правки `.md`** — не только после переименования
заголовка: любая вставленная или удалённая строка сдвигает номера ниже неё, и
оглавление начинает уводить не туда. Это молчаливая поломка, поэтому её сторожит
`backend/tests/test_docs_toc.py` — он падает, если оглавление разошлось с текстом
или если какая-то ссылка `](#…)` никуда не ведёт.

Что при этом надо помнить:

* **правите текст между маркерами `<!-- TOC -->` и `<!-- /TOC -->` — не надо**,
  всё внутри переписывается скриптом;
* **переименовали заголовок — поменялся и его якорь.** Скрипт обновит оглавление
  сам, но ссылки на этот заголовок из **других** файлов он не знает. После
  переименования: `grep -rn "старый-якорь" --include="*.md" .` и почините
  найденное (тест поймает только ссылки внутри того же файла);
* **новый `.md` в корне, `claude/` или `docs/`** обязан получить такую же шапку:
  блок «Зачем этот файл / Когда открывать» и пару маркеров `<!-- TOC -->` и
  `<!-- /TOC -->` подряд, дальше скрипт наполнит их сам. Файла без маркеров тест
  не пропустит;
* **этот файл — исключение** (`NO_TOC` в скрипте): он целиком уезжает в контекст
  ассистента, поэтому оглавления не имеет и не должен разрастаться.

## Как здесь принято работать

* **Не гадать, а измерять.** Почти каждая ошибка в этом проекте случалась там, где
  что-то казалось очевидным. Проверка занимает минуты, разбор последствий — сессию.
* **Ветка `main` защищена, прямой пуш запрещён.** Правки идут веткой и
  пул-реквестом: `git switch -c fix/что-именно && git push -u origin HEAD`,
  пул-реквест создаём сразу при пуше ветки.
* **Правки документации — тем же коммитом, что и код**, который они описывают.
* **Перед коммитом — `git status` и `git diff --cached --stat`.** Первое ловит
  секреты, второе — молчаливый переворот переводов строк (см. ниже): в диффе это
  выглядит как переписанный с нуля файл.

## Чем проверять сделанное

```bash
cd backend && rm -f "$TEMP/a365-tests.sqlite3"* && python -m pytest -q
```

⚠️ **База у тестов одна на весь прогон и переживает прогоны**, поэтому чистить её
перед прогоном обязательно: строка, которую тест добавил и не убрал, достаётся всем
следующим как настоящие данные приложения. На чистой базе так падал двадцать один
тест разом. По той же причине корень библиотеки в тестах берётся только из
`tmp_path` — выдуманный абсолютный путь на Windows молча заводит папку в корне
диска `C:`.

Что чем проверяется — таблица «изменил X → прогони Y» в
[claude/13-workflow.md](claude/13-workflow.md), там же разбор красного CI.

## Чего тесты не поймают

Большинство инвариантов проекта сторожат тесты — про них достаточно знать, что они
есть. Ниже то, что ломается **молча**, поэтому помнить приходится самому (полный
список с обоснованиями — [docs/developer.md](docs/developer.md)):

* **настройки объявляются только в `core/settings_registry.py`** и читаются через
  `settings.get(...)`; прямое обращение к `os.environ` в остальном коде запрещено;
* **новая колонка и новый индекс в существующей базе сами не появляются** —
  за это отвечают `add_missing_columns()` и `sync_indexes()`. Пропуск ничего не
  ломает: всё продолжает работать, просто в тысячу раз медленнее;
* **правите разбор имён, `.nfo` или номеров серий — поднимите `PARSER_REVISION`**
  (`services/library_scan.py`), иначе в базе навсегда останется результат старого
  разбора, а выглядеть это будет как потеря файлов;
* **правите матчер или сканер** — тем же коммитом обновите
  [claude/16-mapping-pipeline.md](claude/16-mapping-pipeline.md) (там записан порядок
  признаков, и именно порядок трижды оказывался причиной ошибки) и найдите либо
  заведите клетку в [claude/15-mapping-matrix.md](claude/15-mapping-matrix.md).

## Грабли окружения

Полный список — раздел «Грабли окружения» в
[claude/13-workflow.md](claude/13-workflow.md). Три, на которых спотыкались по
нескольку раз:

* **переводы строк переворачиваются молча.** На Windows `pathlib.write_text` пишет
  LF как CRLF, а `read_text` схлопывает CRLF в LF при чтении — то есть файл
  переворачивает и связка «прочитал текстом, записал байтами». Файлы проекта
  неоднородны: часть лежит с CRLF, часть с LF, приводить к одному нельзя. Ловится
  только `git diff --cached --stat`: 2532 изменённые строки вместо двух;
* **heredoc в Bash коверкает обратные слэши.** Многострочный Python со спецсимволами
  писать инструментом Write, а не через `<< 'PY'`;
* **Git Bash коверкает пути** в `docker run`/`exec` (нужен префикс
  `MSYS_NO_PATHCONV=1`), падает на кириллице в выводе python
  (`export PYTHONIOENCODING=utf-8`) и не знает про node
  (`export PATH="/c/Program Files/nodejs:$PATH"`).

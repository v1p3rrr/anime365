## 🔴 Правило №0: секреты не попадают в репозиторий

Репозиторий лежит в организации на GitHub (`git@github.com:bocchi-the-server/anime365.git`).
**Попавший в историю секрет остаётся там навсегда**, даже если потом удалить файл, а
`access_token` Anime365 бессрочный и отзывается только сменой пароля.

Что никогда не коммитится:

| Что | Где живёт вместо этого |
|---|---|
| `access_token` Anime365 | `.env` (в `.gitignore`) |
| Пароль на UI | `.env` |
| `jellyfin_api_key` | `.env` |
| Секрет подписи сессий | `config/session_secret` (в `.gitignore`) |
| Оверрайды настроек из UI | `config/settings.yaml` (в `.gitignore`) |
| Личный email | в истории коммитов используется noreply-адрес GitHub |

Как это обеспечивается:
- `.gitignore` исключает `.env*`, `config/settings.yaml`, `config/session_secret`, `*.db`, `data/`;
- в `.env.example` секретные поля **пустые** — он генерируется из реестра настроек, где у таких
  настроек стоит `secret=True`;
- в коде токен наружу не отдаётся (только маска `••••` и флаг `is_set`) и вырезается из логов
  фильтром `SecretRedactingFilter`;
- перед каждым push — проверка `git ls-files` и диффа на предмет токенов.

Проверка вручную:

```bash
git ls-files | grep -iE '\.env$|settings\.yaml|session_secret|\.db$'
git log -p --all | grep -iE 'access_token=[a-f0-9]{32,}'
```

## Итоговая рекомендация

Биндить на `127.0.0.1` или в локальную сеть, доступ через VPN (Tailscale/WireGuard).
Если всё же через Nginx наружу — внешняя аутентификация (Authelia / basic auth) **плюс**
встроенный пароль как второй рубеж, HTTPS, rate limiting, fail2ban.

## 1. Утечка premium-токена

**Риск.** `access_token` бессрочный (до смены пароля). Страница настроек или любой прокси-эндпоинт
дают к нему доступ. Украденный токен = чужой доступ к вашей подписке.

**Меры**
- токен **никогда** не отдаётся в API-ответах — только маска `f1e4…2cbf` и флаг `is_set`;
- подстановка токена только на сервере, в браузер он не попадает вообще;
- отдельный эндпоинт «проверить токен» вместо «показать токен»;
- фильтр-редактор логов: подстрока токена вырезается из всех логов и текстов ошибок
  (иначе он утечёт в трейсбек при первом же сбое CDN).

## 2. SSRF и «вирусный base_url» — главный класс

Это то, про что спрашивал пользователь: правка DOM или тела запроса в браузере не должна ничего
решать. Принцип — **клиент не является источником истины, валидация только на сервере**.

**Меры**
- `base_url` — не свободная строка, а **выбор из четырёх** (`SettingType.ENUM` с
  `choices=DEFAULT_MIRRORS`). Значение не из списка отвергается валидатором реестра,
  то есть произвольный адрес в эту настройку не попадает в принципе;
- `mirrors` (сам allowlist) помечен `server_only`, и это **проверяется на эндпоинте**
  (`api/settings.py`): правка из браузера отвечает ошибкой. Новое зеркало добавляется
  только через ENV на сервере;
- каждая запись allowlist обязана быть `https`-origin без пути и порта (`_check_https_origin`);
- **хост сверяется на каждом шаге редиректа**, а не только у исходной ссылки
  (`downloader.open_checked`). Цепочка проходится вручную с проверкой каждого
  `Location` и потолком в пять шагов, причём `follow_redirects=False` задаётся
  на самом вызове `send()`: иначе защита держалась бы на том, что каждый
  вызывающий не забыл выставить флаг при создании клиента;
- через этот помощник ходят **все четыре** места, добывающие содержимое снаружи:
  поток видео, субтитры, загрузка в библиотеку и проба веса файла. Первая версия
  правки закрыла только два из них — см. предупреждение в [D-174](09-decisions.md);
- допустимые хосты — зеркала из allowlist плюс суффиксы CDN
  (`*.quantum-phantom-moon.ru`, `*.b-cdn.net`), см. `is_allowed_target`;
- **никаких** открытых прокси-эндпоинтов вида `/fetch?url=…`: эндпоинты потока принимают
  идентификатор перевода, а ссылку добывают сами;
- то же касается `jellyfin_url` и `jellyfin_public_url` — оба `server_only` ([D-60](09-decisions.md)).

⚠️ **Чего здесь нет и почему.** Отдельной проверки IP-литералов, приватных диапазонов и
резолва имени **до** обращения (защита от DNS-rebinding) в коде нет. Она не нужна, пока
адрес выбирается из зафиксированного списка: свободной строки, в которую можно вписать
`169.254.169.254`, ни в одном пути нет. Записано явно, потому что раньше этот раздел
обещал такую проверку, а её не было — и следующий читатель мог ослабить `ENUM`, считая,
что снизу страхует разбор адресов. **Ослабляя `base_url` до свободной строки, эту
проверку придётся написать.**

## 3. Запись в ФС и path traversal

**Риск.** Ручной маппинг и постобработка принимают пути от пользователя. `../../etc` или симлинк
наружу = запись куда угодно от имени контейнера.

**Меры**
- путь нормализуется и проверяется как потомок настроенного корня: `Path.resolve()` +
  `is_relative_to(root)`, причём **после** разыменования симлинков;
- запрещены `..`, абсолютные пути вне корней, NUL-байты;
- имена файлов санитизируются: вырезаются `/ \ : * ? " < > |`, управляющие символы, `[` `]`,
  хвостовые точки и пробелы; проверка на зарезервированные имена Windows (`CON`, `PRN`, `AUX`,
  `NUL`, `COM1…9`, `LPT1…9`) — библиотека может лежать на SMB-шаре;
- лимит длины имени (**в байтах**, UTF-8 многобайтовый) и полного пути;
- ⚠️ отдельно важно: `authorsSummary` приходит **с внешнего сайта** и попадает в имя файла —
  это недоверенный ввод, санитизация обязательна (см. [06-naming-rules.md](06-naming-rules.md)).

## 4. SQL-инъекции

**Меры**
- только SQLAlchemy с параметризованными запросами; сырой SQL — исключение, и там только
  bound-параметры, никакой конкатенации строк;
- ⚠️ отдельная осторожность с **FTS5**: пользовательская строка поиска **не** склеивается
  в `MATCH`-выражение, а передаётся параметром и экранируется. Иначе кавычки и операторы FTS
  (`*`, `NEAR`, `OR`, `"`) ломают запрос или дают неожидаемую выборку.

## 5. XSS

**Риск.** Описания тайтлов, названия, имена авторов приходят с внешнего сайта.

**Меры**
- React экранирует по умолчанию; `dangerouslySetInnerHTML` **запрещён** — описания рендерим текстом;
- CSP без `unsafe-inline`;
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`.

## 6. CSRF

**Меры**
- сессионная кука `HttpOnly` + `SameSite=Strict` + `Secure`;
- изменяющие операции только `POST/PUT/DELETE` — никаких мутаций по `GET`;
- проверка `Origin` / `Sec-Fetch-Site`.

## 7. Брутфорс пароля

**Меры (реализовано)**
- пароль, заданный через UI, хранится argon2id-хешем;
- пароль из `A365_UI_PASSWORD` остаётся открытым текстом — заставлять хешировать руками при
  правке `docker-compose` было бы издевательством; сравнение в этом случае идёт
  `hmac.compare_digest` по байтам (для строк он требует чистый ASCII, а пароль вполне может
  оказаться кириллическим);
- **два счётчика попыток** — по адресу (10 за 5 минут) и по имени учётной записи (20 за
  5 минут), плюс пауза 1 с на каждой неудаче и удвоение окна за каждый промах сверх лимита.
  Только по адресу мало: ботнет размазывает попытки. Только по имени тоже мало: так можно
  запереть чужую учётную запись;
- **минимум 8 символов** и запрет пробелов по краям — для паролей, задаваемых через
  интерфейс. Пароль из окружения не проверяется намеренно: отказ на старте означал бы, что
  сервис не поднимется и починить его нечем;
- **сессии — случайные непрозрачные токены в памяти процесса, а не подписанные куки.**
  Подписанным нужен долгоживущий секрет на диске, то есть ещё один файл с секретом.
  Плата за выбор: после перезапуска контейнера нужно войти заново. Для домашнего сервиса
  это скорее плюс;
- смена пароля сбрасывает все сессии, а текущему клиенту сразу выдаётся новая — иначе тот,
  кто только что задал пароль, получил бы `401` на следующем же запросе;
- **сессии отзываются** при удалении пользователя и при смене его пароля администратором:
  иначе удалённый ходил бы по живой куке до её срока ([D-79](09-decisions.md));
- **свой пароль меняет каждый сам** — с вводом текущего и тем же счётчиком попыток, что на
  форме входа. До этого поменять пароль мог только администратор и только чужой;
- если пароль не задан — вход открыт, но UI показывает красное предупреждение на странице
  настроек, а сервис пишет об этом в лог при каждом старте.

## 8. Заполнение диска и DoS

**Риск.** Батч «скачать все видео» на тайтле с 300 сериями — десятки ГБ (1080p ≈ 229 МБ/серия).

**Меры**
- лимит длины очереди;
- проверка свободного места перед стартом задачи + порог `min_free_space_gb`;
- лимит размера тела запроса;
- rate limit на дорогие эндпоинты (онлайн-поиск, `embed`, батч-постановка).

## 8а. Скачивание себе на компьютер

Видео человеку отдаёт не наш сервер, а CDN: мы забираем у Anime365 только
заголовок `Location` и отдаём его браузеру редиректом. Проверено на живом API —
в подписанной ссылке (`…b-cdn.net/route/?m=…&r=…`) токена нет.

Четыре проверки перед тем, как отдать адрес ([D-85](09-decisions.md)): ответ
обязан быть редиректом (без подписки сайт отвечает `200` и HTML-страницей, и
отдать её значило бы показать токен в адресной строке), хост сверяется с тем же
allowlist, что и при скачивании в библиотеку, а если токен всё же оказался в
адресе — отказ. Право — `watch`: тем же токеном человек уже может посмотреть эту
серию целиком.

Файлы с сервера (библиотека, фонотека) отдаются теми же эндпоинтами, что и
проигрывание, с флагом `?download=1`: путь по-прежнему берётся из базы по
идентификатору, а не из параметра запроса.

## 9. Использование вашего премиума как чужого прокси

**Меры** — авторизация обязательна; CDN-ссылки не отдаются анонимно; эндпоинт плеера тоже под сессией
и требует права `watch` ([D-76](09-decisions.md)): раньше видео отдавалось и без него, то есть роль
«пусть смотрит, но ничего не качает» не значила ничего.

## 9а. Права учётных записей

Шесть прав: `catalog` (чтение), `watch` (плеер и фонотека), `device_downloads` (унести файл
себе), `downloads` (очередь), `library` (привязки, сканирование, Jellyfin), `settings`
(серверные настройки, а значит и премиум-токен).
Управление пользователями — только администратор, отдельным правом не выдаётся.

**Каждый** маршрут под `/api/` спрашивает право. Открытых ровно шесть: `/api/health`,
`/api/auth/{status,login,logout}`, `/api/users/me` и `/api/users/me/password` (свой пароль
меняет любой вошедший — там своя защита: текущий пароль и счётчик попыток). Полнота проверяется тестом
`tests/test_permissions_audit.py` — и разбором декораторов, и обходом собранного приложения,
чтобы маршрут, объявленный вне роутеров, не проскочил.

Скрытие кнопок в интерфейсе — удобство поверх серверной проверки, а не её замена.

Подробнее, включая границы («почему очередь читается по `downloads`, а сверка с Jellyfin — по
`library`»), — [D-76](09-decisions.md); таблица «право → эндпоинты → что прячется» —
[docs/admin.md](../docs/admin.md).

## 10. Docker

**Меры**
- медиатома монтировать точечно, `:ro` где можно (корням библиотек rw нужен только для записи
  результатов);
- non-root, PUID/PGID;
- `no-new-privileges: true`, `cap_drop: [ALL]`;
- `read_only: true` для rootfs + tmpfs на `/tmp`;
- **никакого** `network_mode: host`;
- порт публиковать как `127.0.0.1:8080:8080`, если снаружи Nginx.

## Что осталось незакрытым

- **`docker build` не проверялся** — на машине разработки не запускался демон. Compose при
  этом валиден (`docker compose config` проходит).
- **`pip-audit` / `npm audit` в сборке** — версии запинены, но автоматической проверки в
  CI нет: CI как такового пока нет.
- **Лимит длины очереди** не реализован. Частично закрыт лимитом батча (2000 задач за раз)
  и ограничителем частоты (20 батчей в минуту), плюс проверкой свободного места перед стартом.

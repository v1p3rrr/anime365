# Журнал решений

Каждая запись: что решили, почему, и что было альтернативой. Если решение отменяется — не удаляем,
а помечаем `ОТМЕНЕНО` с причиной.

---

## D-01. Backend: Python 3.12 + FastAPI

**Решил пользователь.** Знает Java/Spring и Kotlin хорошо, Python-синтаксис знает, фреймворки — нет.

Почему Python: 100–180 МБ RSS против 350–500 у Spring Boot на сервере с 16 ГБ и слабой частотой;
asyncio идеально ложится на профиль задачи («качать файлы + опрашивать API» = сплошной I/O);
кода на ту же логику заметно меньше. FastAPI — один из самых простых фреймворков для входа,
с автогенерацией OpenAPI (что заодно упрощает отладку руками).

---

## D-02. БД: SQLite в режиме WAL

Каталог — 29 231 тайтл, ~25 МБ. Нагрузки нет, пользователей 2–3. PostgreSQL — это +контейнер
и +150 МБ ОЗУ ради ничего. Бэкап = копия файла. WAL нужен, чтобы читатели не блокировали писателя
(фоновый синк каталога идёт одновременно с просмотром UI).

Альтернатива (PostgreSQL) отклонена: выигрыш только при конкурентной записи, которой здесь нет.

---

## D-03. Пагинация каталога: виртуализированный скролл по полному списку id

**Не** бесконечный скролл с догрузкой, **не** кнопка «показать ещё», **не** странички 1-2-3.

Запрос с фильтрами возвращает только массив id подходящих тайтлов (29 231 id ≈ 200 КБ JSON;
каталог и так локально в SQLite, поэтому быстро), фронт строит виртуальный список нужной длины
и подгружает данные карточек окнами по 100.

Почему так:
- полоса прокрутки **сразу правильной длины**, можно прыгнуть в любое место;
- нет классических багов infinite scroll: дублей на границе страниц, «прыгающего» скролла,
  потери позиции при возврате со страницы тайтла (позиция = индекс в списке);
- проще отлаживать: состояние это `(фильтры) → список id` + кэш окон, а не «сколько страниц
  я подтянул и в каком порядке»;
- отбор и сортировка — один SQL-запрос на сервере, фронт не дублирует логику фильтрации.

---

## D-04. Именование скачанных видео: по образцу соседей, с заменой релиз-группы

**Решил пользователь.** Берём паттерн соседних файлов в целевой папке и заменяем `[Группа]` на
`[anime365_{Автор перевода}]`. Так библиотека остаётся консистентной для Jellyfin.

Альтернативы отклонены: своя каноническая схема всегда → имена разъедутся с соседними эпизодами;
оставлять `[Anime365] … (t123456).mp4` → Jellyfin хуже распознаёт такие имена в существующих папках.

---

## D-05. Метка источника — всегда `WEBDL`

**Решил пользователь.** Даже если соседние эпизоды помечены `Bluray-1080p` или `HDTV-1080p`,
у наших файлов пишем `WEBDL-{height}p`. Всё, что приходит с Anime365, — это WEBDL, и врать
в имени файла не будем.

Важное исключение: при докачке **только субтитров** basename соседнего видеофайла берётся
**как есть**, вместе с его `Bluray-1080p` — иначе порвётся связь «видео ↔ сабы».
Правило `WEBDL` применяется только к именам, которые мы создаём сами.

---

## D-06. Имя докачанных субтитров: `{basename видео}.anime365_{Автор}.{lang}.ass`

**Решил пользователь.** Jellyfin подхватывает сабы только при совпадении basename с видеофайлом.
Вставка автора позволяет держать несколько переводов на один эпизод (иначе второй русский перевод
затирал бы первый).

Альтернативы отклонены: `{basename}.{lang}.ass` → коллизии при нескольких переводах;
конвертация в `.srt` → потеря оформления и караоке, а Jellyfin и так умеет `.ass`.

---

## D-07. Настройки: три слоя `дефолт в коде < ENV < UI`

**Решил пользователь.** Реализация: `pydantic-settings` читает дефолты и ENV, поверх накладывается
таблица `app_setting`.

Ключевое требование к реализации: **каждая настройка объявляется один раз** в едином реестре
(имя, тип, дефолт, имя ENV, валидатор, признак секретности), и из него генерируются ENV-парсинг,
форма в UI и `.env.example`. Иначе три слоя неизбежно разъедутся между собой.

В UI у каждого поля видно, **откуда** взято значение (`по умолчанию` / `из ENV` / `изменено в UI`),
и есть кнопка сброса (удаляет запись из БД, значение возвращается к ENV/дефолту).

---

## D-08. Пользовательские настройки — в браузере, не на сервере

**Решил пользователь** (сайт могут одновременно использовать 2–3 человека).

В `localStorage`: выбранные языки переводов, включённые типы (озвучка/сабы/raw), фильтры каталога,
режим сетка/таблица, тогглы значков, язык интерфейса, сортировка. Это именно то, что должно
различаться у разных людей, и это не требует ни аккаунтов, ни серверных сессий.

Серверные настройки (пути, токен, лимиты, расписания) остаются общими — они про поведение сервиса,
а не про вкусы конкретного человека.

---

## D-09. Аккаунтов пока нет, но схема готовится

**Решил пользователь.** Сейчас — один общий пароль на UI. Чтобы позже добавить аккаунты без боли:

- таблица `app_user` создаётся сразу, с единственной строкой `id=1, name='default'`;
- пользовательские сущности (очередь загрузок, ручные маппинги) с самого начала имеют
  `created_by_user_id` = 1;
- клиентские настройки в `localStorage` лежат под версионированным префиксом, чтобы их можно было
  перенести в серверный профиль миграцией, а не переписыванием UI;
- все изменяющие операции идемпотентны по ключу (`translation_id + тип + качество`), поэтому два
  человека, нажавшие «скачать» на одном переводе, не создадут две задачи.

Тогда включение аккаунтов = строки в `app_user` + логины вместо общего пароля + перестать
игнорировать `created_by_user_id`. Схема и эндпоинты не меняются.

## D-10. Обновление кэша: раз в час инкремент, раз в сутки полный рескан

Пользователь попросил «по умолчанию раз в час, значение в часах в настройках».

Разделено на два интервала, потому что полный скан — 44 запроса и 32 секунды, гонять его каждый
час бессмысленно:
- `catalog_refresh_hours` (по умолчанию **1**) → инкремент по `afterId` + обновление онгоингов
  (306 тайтлов) — секунды;
- `catalog_full_refresh_hours` (по умолчанию **24**) → полный рескан, ловит правки существующих
  тайтлов (у series нет `updatedDateTime`, поэтому иначе их не увидеть).

## D-11. Матчинг: строковый алгоритм основной, ID из `.nfo` — только ускоритель

**Уточнил пользователь:** у части аниме может не быть shikimori-id, и полагаться на ID нельзя.

Факты: `anilistId` заполнен у 19 030 тайтлов из 29 231, `myAnimeListId` — у 28 566, а в самих `.nfo`
соответствующих тегов может не быть вовсе (зависит от плагина Jellyfin). Плюс проверка показала,
что `<shikimoriid>` бывает попросту неверным (у YuruYuri указывает на «Pu-Neko»).

→ Строковый каскад обязан работать полностью самостоятельно. ID-шаги лишь снимают часть нагрузки
и повышают уверенность там, где данные есть. Подробно — [05-matching-algorithm.md](05-matching-algorithm.md).

---

## D-12. Сезоны разводятся по `<premiered>` из `season.nfo`

ID сезона в `season.nfo` нет (только `tvdbid`, которому в Anime365 ничего не соответствует).
Но есть `<premiered>`, и он отображается на поле `season` каталога («2012-07-02» → «Лето 2012»).

Проверено на YuruYuri, где в каталоге 8 похожих тайтлов: даты премьеры разводят Season 1/2/3
и Specials однозначно, тогда как одного `<year>` **не хватает** (в 2015-м у YuruYuri ещё OVA
«Зима 2015» и tv_special «Лето 2015»).

## D-13. Парсер имён файлов — правила в YAML, а не в коде

**Попросил пользователь**, чтобы после реализации прислать полный список файлов и дописать правила.

Регэкспы живут в `config/filename_rules.yaml`: упорядоченный список правил с приоритетами,
именованными группами и флагом вкл/выкл. Плюс dry-run эндпоинт и CLI, которым можно скормить
хоть весь `tree`, и корпус регрессионных тестов, чтобы новое правило не ломало разобранное ранее.

## D-14. Play: и встроенный плеер, и ссылка на сайт

ТЗ предлагало выбрать одно из двух. Делаем оба — это дёшево и закрывает разные сценарии:
встроенный плеер (`<video>` + ASS через JASSUB/libass-wasm) для быстрого просмотра, ссылка на
страницу серии на сайте — как надёжный фолбек, когда плеер не справился с кодеком или сабами.

## D-15. Хардсаб/софтсаб и точные ступени качества — только лениво

Оба признака доступны исключительно через `embed`, то есть **один запрос на перевод**, а у тайтла
бывает ~2000 переводов. Поэтому:
- при раскрытии группы переводов — запрашиваем `embed` только для показанных;
- результат кэшируем в БД;
- воркер перед скачиванием запрашивает `embed` заново (ссылки подписанные и живут недолго);
- для сводки по качеству используем `height` из дешёвого списочного запроса как **оценку**,
  с явной подписью в UI и кнопкой «уточнить» (дотягивает `embed` по всем эпизодам с прогрессом).

## D-16. Роль ffprobe сужена

Изначально планировался опциональный массовый проход ffprobe для определения вшитых дорожек.
После получения реальных `.nfo` выяснилось, что Jellyfin **уже записал** список дорожек в
`<fileinfo><streamdetails>` — с кодеками и языками субтитров и аудио. Это бесплатно и мгновенно.

→ ffprobe остаётся только для файлов, у которых `.nfo` нет или в нём нет `<streamdetails>`,
и только по кнопке для конкретного тайтла, за выключенным тогглом. Массовый прогон по библиотеке
не делаем — на слабом сервере это часы работы ради данных, которые в основном уже есть.

Оговорка: `streamdetails` не идеальны (у Fate HF I у видеодорожки стоит `language: ita` — явная
чушь), поэтому считаем их подсказкой, а не истиной.

---

## D-17. Интеграция с Jellyfin сужена до одной операции

Изначально рассматривалась как альтернативный источник маппинга. Но `.nfo` рядом с файлами дают
то же самое и без зависимости от живого Jellyfin, его URL, api-key и трансляции путей.

Реально полезное остаётся одно: **пинок «пересканируй папку»** после того, как мы положили файлы,
чтобы новые серии появлялись в Jellyfin сразу, а не по его расписанию. Это и делаем — за
выключенным тогглом, в самом конце.

Побочно выяснено из `.nfo`: Jellyfin монтирует `~/media/anime/library` как `/media/anime`,
поэтому любая интеграция потребует таблицы трансляции путей контейнер↔хост.

## D-18. CDN: через API не выбирается; прямой Bunny-хост — эксперимент за тогглом

Проверено, что параметры запроса на выбор CDN не влияют, а меняющиеся хосты
`ru-NNNNNN.quantum-phantom-moon.ru` — это домен-фронтинг поверх **одного** nginx-прокси перед
одной зоной BunnyCDN. Поэтому идея «перезапрос → другая нода → быстрее» отброшена как неверная.

Зато прямой Bunny-хост принимает подписанную ссылку (206), и на тестовом файле он был в 5.6 раза
быстрее прокси. Но замер на реальном видео воспроизвести не удалось (подписи одноразовые),
и все измерения делались не из сети пользователя.

→ Делаем **опциональный тоггл**, выключенный по умолчанию, с автоматическим откатом на прокси
и замером скорости в логах. Гипотеза проверяется на месте, ничего не ломая, если не подтвердится.

## D-20. Слежение за ФС (inotify) как основной механизм + редкий сверочный скан

**Попросил пользователь:** «либо отслеживать файловую систему, либо по расписанию; если первое
по ресурсам не бьёт — лучше первое».

По ресурсам действительно почти бесплатно: следим за **каталогами**, а не файлами. Библиотека
из ~500 тайтлов с сезонными подпапками — это порядка 1–2 тысяч каталогов, то есть ~1–2 МБ памяти
ядра (одна inotify-watch ≈ 1 КБ) и нулевой CPU в простое. Реализация — `watchdog`.

**Но расписание всё равно остаётся**, потому что у inotify есть два режима отказа, оба тихие:

1. **Сетевые ФС.** На NFS и SMB/CIFS события от других хостов не доставляются вообще. Сейчас
   медиа — bind-mount локального диска, так что всё в порядке, но если библиотека переедет
   на шару, слежение молча перестанет что-либо видеть.
2. **`fs.inotify.max_user_watches`.** На старых системах лимит 8192. При упоре в него watchdog
   деградирует без внятной ошибки.

Поэтому:
- `watch_filesystem` (по умолчанию **включено**) — реакция на изменения почти мгновенная;
- `library_scan_hours` поднят с 6 до **24** и превращён в сверочный проход: ловит пропущенные
  события, изменения во время простоя контейнера и случай сетевой ФС;
- при недоступности inotify или упоре в лимит — **автоматический откат на расписание**,
  предупреждение в лог и видимый статус в UI (пользователь должен знать, что живёт на расписании,
  а не думать, что слежение работает);
- **дебаунс** `watch_debounce_seconds` (по умолчанию 10 с): копирование одного файла порождает
  десятки событий, поэтому ждём тишины по папке и только потом пересканируем **её одну**,
  а не всю библиотеку.

Дополнительно: события порождают и сами Jellyfin/Sonarr, когда пишут `.nfo` и постеры рядом
с видео. Фильтруем по расширениям, иначе будем гонять скан на каждую перезапись метаданных.

**Целевая платформа — Ubuntu Server.** Практические следствия:
- на современной Ubuntu `fs.inotify.max_user_watches` = 65 536, запас более чем достаточный
  (1–2 тысячи каталогов), но на старых системах бывает 8192 — проверка при старте обязательна;
- лимит **общий на пользователя**, а Jellyfin и Sonarr тоже расходуют watch'и из него;
- дефолтный пользователь Ubuntu — `1000:1000`, поэтому дефолты `puid`/`pgid` совпадают
  и права на созданных файлах обычно сходятся без правки настроек;
- разработка на Windows возможна (достаточно задать `A365_DB_PATH`), но `watchdog` там использует
  другой механизм, поэтому поведение слежения проверяется только на Linux.

## D-21. Основная папка при нескольких привязках

Вопрос пользователя «в каком сценарии папок больше одной» проверен по реальной библиотеке:
таких тайтлов **26**, схема везде одна — один и тот же сезон лежит и разложенным под Jellyfin,
и исходным релизом в другом кодеке (Yuru Camp, Panty & Stocking, Honzuki no Gekokujou, Toradora).

Это вскрыло пробел: при нескольких папках было неясно, куда класть скачанное. Из трёх вариантов
(основная папка / спрашивать каждый раз / класть туда, где больше файлов) выбран первый:
второй раздражает при батч-загрузке, третий молча принимает решение и может положить файл
в папку с чужим кодеком.

Автовыбор ранжирует по вкладу **именно в этот тайтл**, а не по числу файлов в папке: папка может
содержать серии другого сезона, и её размер тогда ничего не говорит. Отдельный флаг
`primary_is_manual` отличает выбор пользователя от автоматического — без него устаревший
автовыбор нельзя пересмотреть, он выглядел бы как решение пользователя.

## D-22. Счётчики наличия считают серии, а не файлы

Из-за нескольких папок один эпизод может лежать в двух копиях. Подсчёт по файлам давал бы
«24 из 12» — очевидное враньё. Считаем **различные номера серий**.

Но молча схлопывать тоже неверно: пользователь не узнал бы, что половина места занята дублями.
Поэтому три уровня: дедуплицированный счётчик, отдельная строка «в двух копиях: 1–12» и
разбивка по папкам, когда папок несколько.

## D-23. Метка активной задачи в очереди — ноль, а не единица

Уникальность задачи действует только среди незавершённых, поэтому у завершённых в поле
`active_key` кладётся их собственный идентификатор, а у активных — константа.

Первая версия использовала единицу, и завершённая задача №1 навсегда блокировала повторную
постановку того же перевода: её `active_key` совпадал с меткой активности. Метка переведена
на ноль — идентификаторов с нулём не бывает.

---

## D-19. Отметки просмотренного не делаем

В API Anime365 нет ни одного эндпоинта для списков/статусов (проверено, см.
[02-api-findings.md](02-api-findings.md)). Реализовать можно было бы только через прямую интеграцию
с Shikimori/AniList — это отдельный OAuth и отдельный объём работы. В текущий проект не входит,
записано в [08-open-questions.md](08-open-questions.md) как идея.

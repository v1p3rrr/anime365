## Правила работы

* **Коммитить и пушить регулярно**, а не в конце. Пользователь про это
  напоминал; целый день несохранённой работы — плохо.
* **Перед коммитом проверить, что нет секретов.** Токен Anime365 лежит в `.env`
  (по просьбе пользователя), ключ Jellyfin передаётся переменной окружения.
  `.env`, `config/`, `data/`, `temp/` — в `.gitignore`, это проверено
  `git check-ignore`. Ни то ни другое не должно попадать ни в код, ни в
  документацию, ни в примеры команд.
  Проверка перед коммитом: `git diff --cached | grep -oE "\b[a-f0-9]{32,}\b"`
  (пусто = чисто).
* **Не гадать, а измерять.** Почти каждая ошибка в этом проекте была там, где
  что-то казалось очевидным: что `st_dev` достаточно, что логотипы всегда
  `.png`, что `follow_redirects` не нужен. Проверка занимает минуты.
* **Правки документации — вместе с кодом**, в том же коммите. Разъехавшаяся
  документация обнаруживается через недели.
* **Оглавления пересчитывает хук.** Включается один раз на машину:
  `git config core.hooksPath scripts/hooks`. Он запускает
  `scripts/update_docs_toc.py` перед коммитом и доносит в него **только те**
  `.md`, которые в коммите и так были. Без хука остаётся ручной запуск, а
  забытый ловит `backend/tests/test_docs_toc.py` — но уже после коммита.
* **После любой правки `.md` — `python scripts/update_docs_toc.py`.** У каждого
  документа сверху таблица «строка → раздел», и любая вставленная строка сдвигает
  номера ниже неё. Ломается это молча: оглавление выглядит правдоподобно и уводит
  не туда. Номера руками не правим — их считает скрипт, а сторожит
  `tests/test_docs_toc.py`.
* **Переименовали заголовок — проверьте ссылки на него из других файлов:**
  `grep -rn "старый-якорь" --include="*.md" .`. Внутри своего файла битую ссылку
  поймает тест, чужую — нет.
* **Читать документацию тоже надо через оглавление**: сначала верх файла (сводка
  «зачем он» плюс таблица разделов), потом нужный кусок по номеру строки. Правило
  для ассистента записано в [CLAUDE.md](../CLAUDE.md).

уезжают.

## Команды

Сборка и запуск для проверки:

```
docker build -t anime365-downloader:0.1.0 .
docker run -d --name a365-test -p 8099:8080 --env-file .env \
  -v "<репозиторий>/temp:/media/animeseries:ro" \
  -v "<scratchpad>/mnttest:/media/rw" \
  -v "<scratchpad>/a365data:/data" \
  -e A365_SERIES_ROOT=/media/animeseries -e A365_MOVIES_ROOT=/media/rw/movies \
  -e A365_AUDIO_ROOT=/media/rw/audio -e A365_DOWNLOAD_TMP=/media/rw/.a365-tmp \
  -e A365_DB_PATH=/data/app.sqlite3 anime365-downloader:0.1.0
```

Три вещи здесь важны, и все три — по просьбе пользователя:

* **`temp/` монтируется корнем сериалов, только на чтение.** Там настоящее
  аниме с `.nfo` и субтитрами: сканер, разбор имён и маппинг надо проверять на
  нём, а не на выдуманных папках. `ro` — чтобы ничего нельзя было испортить.
  На полном каталоге маппинг сходится: 6 папок из 6;
* **база лежит в scratchpad, а не в контейнере.** Иначе каталог сносится при
  каждой пересборке и синхронизировать приходится заново. Полный каталог —
  29 214 тайтлов, около минуты. **Каталог обновлять, а не сносить:**
  `POST /api/catalog/sync {"mode":"incremental"}`;
* **`--env-file .env`** даёт токен Anime365.

Тесты **внутри образа** — так проверяется тот стек, что поедет на сервер:

```
docker run --rm --entrypoint sh -v "$PWD:/repo:ro" -u root anime365-downloader:0.1.0 \
  -c "pip install -q pytest; cd /repo/backend && PYTHONPATH=/repo/backend python -m pytest tests -q"
```

Наполнить каталог для проверки: `POST /api/catalog/sync {"mode":"airing"}` даёт
306 онгоингов за секунды; `search-online?query=…` подтягивает конкретный тайтл.

## Грабли окружения

* **Git Bash коверкает пути** в `docker run`/`exec`: `/data/app.sqlite3`
  превращается в `C:/Program Files/Git/data/...`. Лечится префиксом
  `MSYS_NO_PATHCONV=1` перед командой.
* **`docker restart` не подхватывает новый образ.** Нужно `docker rm -f` и
  `docker run` заново. На этом дважды разглядывался старый бандл.
* **Браузер кэширует `index.html`.** После пересборки образа страница может
  выполнять старый бандл — и это выглядит как «баг вернулся»: пропавшие элементы,
  чужие ошибки React в консоли. На это уже уходил час впустую.
  Проверять так:

  ```js
  fetch('/?x=' + Date.now()).then(r => r.text()).then(h => console.log(
    'сервер отдаёт:', h.match(/assets\/index-[^"]+\.js/)[0],
    'браузер выполняет:', [...document.scripts].map(s => s.src)))
  ```

  Не совпало — открыть `/` с новым query, обычной перезагрузки может не хватить.
* **Буфер `read_console_messages` не чистится** ни `console.clear()`, ни
  переходом. Старые записи выглядят как свежие; отличать их надо по имени бандла
  в стеке. Надёжнее подменить `console.error` своим сборщиком в `window`.
* **Замеры скорости с Windows врут.** Через проброс портов Docker Desktop любой
  ответ, включая статический файл, стоит около 220 мс. Мерить — изнутри
  контейнера.
* **Переводы строк переворачиваются скриптом молча.** `pathlib.write_text` на
  Windows пишет `\n` как `\r\n`, а `read_text` наоборот схлопывает
  `\r\n` в `\n` при чтении. Поэтому переворачивает файл и связка
  «прочитал текстом — записал байтами»: одного `write_bytes` мало, читать тоже
  надо байтами.

  В диффе это выглядит как переписанный с нуля файл: **2532** изменённых строки
  вместо двух в `12-questions.md`, **1293** вместо 39 в `autodownload.py`.
  Ловится только `git diff --cached --stat` — смотреть его перед коммитом
  обязательно.

  ⚠️ Файлы проекта неоднородны: `claude/00-INDEX.md` и часть кода лежат с CRLF,
  остальное с LF. Приводить всё к одному нельзя — это и будет тот самый дифф на
  весь файл.
* **Локально `backend/app/static/` есть, в CI его нет.** Каталог со сборкой
  фронтенда в `.gitignore`, но у разработчика он лежит с прошлой сборки — и от
  этого зависит поведение сервера: заглушка SPA регистрируется, только если он
  существует. Незнакомый путь на своей машине получает страницу приложения, а на
  чистой — 404. Тест входа так и жил годами, дёргая несуществующий
  `/api/catalog` ([D-164](09-decisions.md)). Проверять подозрительное так:
  `mv backend/app/static /tmp/ && python -m pytest -q`.
* **Тестовая база одна на весь прогон.** Строка, которую тест добавил и не
  убрал, достаётся всем следующим как настоящие данные приложения. Корень
  библиотеки с выдуманным абсолютным путём на Windows при этом молча создаёт
  папку в корне диска C: — прогон тестов годами делал это незаметно
  ([D-165](09-decisions.md)). Корень в тестах — только из `tmp_path`; выдуманный
  путь обязан убираться в teardown.
* **Локальный `pytest` — не тот, что объявлен в `pyproject.toml`.** В окружении
  стоит свой (9.1.1 против пина 9.0.3), и ставится он не из списка зависимостей.
  Из-за этого противоречие внутри самого списка может не проявляться годами:
  `pytest-asyncio==0.25.2` требовал `pytest<9` и с пином `9.0.3` не
  устанавливался в принципе, а локально никто и не пытался. Поймал это первый же
  прогон CI на чистой машине. Проверять список целиком:
  `pip install --dry-run -r <список>`.
* **Локальная БД разработчика — тестовая**, каталога в ней нет. Реальные данные
  только в контейнере.
* **Временная БД тестов переживает прогоны** (`/tmp/a365-tests.sqlite3`). Из-за
  этого тесты, зависящие от порядка, на своей машине проходят, а на чистой —
  нет. Проверять на свежем контейнере.
* **Перетаскивание синтетическими событиями не проверить.** dnd-kit опирается
  на захват указателя (`setPointerCapture`), а его у выдуманных `PointerEvent`
  нет; клавиатурный путь тоже не отрабатывает. Проверять — руками в браузере.
* **Кириллица в теле `curl` через Git Bash искажается.** Пароль доезжал до
  контейнера верно, а запрос уходил с другими байтами — выглядело как «вход не
  работает». Проверять учётные данные на латинице.
* **Вывод python в Git Bash падает на кириллице.** `UnicodeEncodeError: charmap`
  — нужен `export PYTHONIOENCODING=utf-8` перед разбором JSON-ответов.
* **`subprocess` с `encoding="utf-8"` не читает stderr дочернего процесса на
  Windows.** Тот пишет в кодировке консоли (cp1251), поток-читатель падает с
  `UnicodeDecodeError`, а `result.stderr` молча становится `None` — тест
  разваливается не там, где смотрит. Нужен `errors="replace"`.
* **`node`/`npm` не на PATH** в Bash-инструменте: нужен
  `export PATH="/c/Program Files/nodejs:$PATH"`.
* **Python в Bash — виндовый.** `subprocess.run(['find', ...])` вызовет
  `find.exe` — совсем другую утилиту, и проверка тихо вернёт пустой результат.
  Использовать `pathlib`.
* **Ссылка на решение внутри `09-decisions.md` — только полным слагом.**
  `[D-140](#d-140)` ведёт в никуда: якорь собирается из **всего** заголовка
  («d-140-пустая-подпапка-не-мапится…»). Короткую форму ловит
  `test_anchors_lead_somewhere`, но уже после правки. Проще писать `D-140`
  текстом — так сделано у большинства перекрёстных ссылок.
* **Heredoc в Bash коверкает обратные слэши.** Многострочный Python со
  спецсимволами лучше писать инструментом Write, а не через `<< 'PY'`.
* **Windows не заводит папки с `:` в имени.** В библиотеке есть
  `Gate: Jieitai Kanochi nite, Kaku Tatakaeri`, поэтому воспроизводить раскладку
  надо **внутри контейнера**, а не в scratchpad.
* **Воссоздавая библиотеку для проверок, имена файлов брать настоящие.**
  Спешлы опознаются по имени файла: назвав их по имени подпапки
  (`Specials S00E01.mkv`), получите ложный вывод «спешлы не работают».
* **Пересоздание контейнера из образа откатывает подложенный код.** После
  `docker rm -f` + `docker run` правки, скопированные через `docker cp`,
  исчезают — и прогон идёт по старому коду.

## Что проверять после правок

| Изменил | Проверить |
|---|---|
| Новый эндпоинт | `tests/test_permissions_audit.py` — маршрут без права роняет тест. И спрятать соответствующую кнопку в UI через `usePermissions` |
| Зависимости | Только `backend/pyproject.toml` — образ ставит по нему (D-167). `tests/test_dockerfile_deps.py` сторожит, чтобы прибитые версии не вернулись в `Dockerfile` |
| Настройку в реестре | `tests/test_compose_env.py` и `tests/test_settings_i18n_sync.py` — переменная должна попасть в compose, а подписи в `ru.ts` совпадать дословно |
| Dockerfile | Пересобрать и **прогнать скан**; проверить, что зачистка сработала (там стоят `test !`, но лишним не будет) |
| Фронтенд | `tsc --noEmit`, `npm run lint`, `npm run build`. Линтер ловит хуки после раннего `return` — компилятор такое пропускает, а страница падает в браузере |
| Индекс или запрос каталога | `tests/test_catalog_indexes.py` — **каждое** обращение к `series` в плане обязано быть покрывающим, и тест перебирает 60 сочетаний фильтров с сортировками. Одного `COVERING` где-то в плане мало: так пропустили фильтр по сезону с сортировкой по оценке за 4,7 с. Новый фильтр в каталоге — это и новая колонка во всех четырёх индексах, и новая строка в `_FILTERS` теста |
| Сортировку в каталоге | Ещё и `SORT_INDEX` в `api/catalog.py`: индекс называется явно, и без записи в таблице запрос просто упадёт |
| Транзакции | `tests/test_db_locking.py` и `tests/test_transaction_hygiene.py` — границы транзакций и запрет `await` внутри них |
| Любой `.md` | `python scripts/update_docs_toc.py`, дальше `tests/test_docs_toc.py`. Номера строк в оглавлениях сдвигает **любая** вставленная строка, не только новый заголовок |
| Матчер или сканер | `claude/16-mapping-pipeline.md` — документ описывает **порядок признаков** и список вето, и обновлять его надо тем же коммитом |
| Сканер библиотеки | Ещё и `tests/test_scan_scope.py`: инкремент обязан пересопоставлять **только** изменившееся, иначе один новый файл снова будет стоить пересчёта всей библиотеки ([D-155](09-decisions.md)) |
| Номер версии | `tests/test_version_is_one.py` — он лежит в пяти местах, а пайплайн клеит на образ тот, что в `pyproject.toml` ([D-161](09-decisions.md)) |
| `.dockerignore` | `tests/test_dockerignore.py` — контекст сборки не должен терять то, что копирует `COPY`; проверять настоящей сборкой дорого, поэтому тест разбирает шаблоны сам ([D-162](09-decisions.md)) |
| Что угодно | Все тесты, и лучше внутри образа |

## Что тормозит: как смотреть, а не гадать

⚠️ Главная ошибка прошлой сессии — доказывать медленность косвенно. Пауза между
проверками здоровья контейнера доказывает лишь занятость процесса, и выдавать её
за время ответа нельзя ([D-154](09-decisions.md)).

Прямые источники, все в логе контейнера:

```bash
# Медленные запросы: дольше A365_SLOW_REQUEST_MS (по умолчанию 1000 мс)
docker logs anime365-downloader 2>&1 | grep "WARNING  app.access"

# Время скана по этапам: обход / запись / сопоставление / связка серий
docker logs anime365-downloader 2>&1 | grep "Корень /media"

# Как часто вообще запускается скан — при активной загрузке их бывает десятки в час
docker logs anime365-downloader 2>&1 | grep "Изменения в библиотеке"
```

Порядок величин на живой библиотеке (591 папка, 11 516 файлов, 29 351 тайтл в
каталоге), чтобы было с чем сравнивать:

| Что | Сколько |
|---|---:|
| запрос каталога с фильтром и счётчиком | 16 мс |
| обход диска, оба корня | ~7 с |
| сопоставление одной папки | ~0,12 с |
| полный проход со всем сопоставлением | ~118 с |

То есть **сопоставление дороже диска на порядок**, и это питоновский счёт в том
же процессе, а не база. SQLite на этих объёмах не бывает узким местом — прежде
чем подозревать её, посмотрите на два верхних грепа.

Уровни логирования правятся в `config/logging.yaml`, разово — переменными
`A365_LOG_LEVEL` и `A365_LOG_LEVELS` ([D-158](09-decisions.md)).

## Запросы к Anime365 не отвечают: что смотреть

Строка отказа теперь несёт всё, что нужно, чтобы не гадать
([D-169](09-decisions.md)):

```bash
docker logs anime365-downloader 2>&1 | grep "Зеркало"
```

Как её читать:

| Что в строке | О чём говорит |
|---|---|
| `ждал ответа ~10000 мс` | упёрлись в `connect=10.0` — сеть молчала |
| `ждал ответа 30 мс` | отказали сразу: DNS, отказ в соединении, сброс |
| `в очереди лимитера` большое | до сети дело шло долго, виноват темп запросов |
| `маршрут: напрямую (…)` | запрос пошёл **мимо** прокси — почти всегда это и есть причина |
| `одновременных запросов: 40` | прокси задавили мы сами |

Тайминги каждого успешного запроса — по требованию:

```bash
A365_LOG_LEVELS=app.services.anime365=DEBUG
```

⚠️ Одинаковые таймауты подряд **не** означают, что сеть лежит. Проверять надо из
того же контейнера, а не с рабочей машины:

```bash
docker exec anime365-downloader python -c "import httpx;print(httpx.get('https://smotret-anime.org/').status_code)"
```

Именно так выяснилось, что сеть исправна, а виноват был бесконечный повтор
([D-168](09-decisions.md)).

## CI: что там гоняется и как его чинить

Настройка учётных данных, теги образа и проверка подписи — в
[../docs/developer.md](../docs/developer.md), раздел «Сборка в GitHub». Здесь —
то, что нужно, когда прогон уже красный.

**Прогон повторяет локальные команды один в один**, так что чинить всё
воспроизводится на своей машине:

```bash
cd backend && python -m pytest -q
```

```bash
cd frontend && npm ci && npm run build
```

Разница ровно одна и важная: **база на раннере всегда чистая**. Локально
`/tmp/a365-tests.sqlite3` переживает прогоны, и тест, зависящий от порядка, у
вас зелёный, а в CI красный. Воспроизводить так:

```bash
cd backend && rm -f "$TEMP/a365-tests.sqlite3"* && python -m pytest -q
```

**Работа `image` собирает образ и гоняет по нему Trivy** с порогом CRITICAL и
`ignore-unfixed`. Упало — значит в базовом образе появилась уязвимость, у
которой **уже есть исправление**: чинится обновлением `python:3.12-slim` или
`node:22-alpine`, а не правкой порога. Посмотреть то же самое локально:

```bash
docker build -t anime365-downloader:ci . && trivy image --severity CRITICAL --ignore-unfixed anime365-downloader:ci
```

⚠️ **Работа `image` тянет базовые образы из Docker Hub без входа** — иначе
секрет пришлось бы отдать работе, которая идёт и по пул-реквестам, а это ровно
то, чего мы избегаем ([D-160](09-decisions.md)). Плата за это — редкий отказ
`toomanyrequests` при холодном кэше. Лечится повтором прогона. Переносить сборку
в `publish` — **не** лечение: у той работы нет ни репозитория, ни сборщика, и
это сделано намеренно ([D-163](09-decisions.md)).

**Работа `publish` не запускается по пул-реквесту** и не запустится, даже если
очень нужно: у неё `if: github.event_name == 'push'`. Проверить сборку образа
до слияния можно и без неё — этим занята `image`.

**`publish` не собирает образ и не выкачивает репозиторий.** Она получает
готовый архив от `image`, распаковывает его `docker load` и толкает в реестр
([D-163](09-decisions.md)). Поэтому чинить там нечего: если образ собрался не
так, смотреть надо в `image`. А если упал сам `docker push` — это реестр,
учётные данные или сеть, и никак не код проекта.

⚠️ **Действия прибиты к хешам коммитов.** Менять версию действия, правя
комментарий `# v4.2.0`, бесполезно — работает то, что в хеше. Обновляет их
Dependabot; руками — только вместе с новым хешем, взять его так:

```bash
git ls-remote https://github.com/docker/build-push-action 'refs/tags/v7.3.0^{}'
```
